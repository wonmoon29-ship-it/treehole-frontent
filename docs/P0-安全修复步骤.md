# P0 安全修复：操作步骤

> 写于 2026-10-10。请**严格按顺序**操作，每一步验证通过后再进行下一步。
> 第 2 步和第 6 步的 SQL 都可以重复运行；如果出错，把报错截图发给我即可。

## 这次修复了什么

| 编号 | 问题 | 修复方式 |
|---|---|---|
| 1 | 任何人都能读到所有人的身份 token，并用它冒充别人 | 发帖改为调用数据库函数；token 列对访客完全不可读 |
| 2 | 绊码是不加盐的 SHA-256，弱暗号可被离线破解 | 浏览器先做 PBKDF2（60 万次迭代），数据库再用私密 pepper 做 HMAC |
| 3 | 访客可以自己指定号码、发帖时间、隐藏状态，内容长度也没有限制 | 这些字段一律由数据库决定；内容限制在 1–200 字；已被伪造的数据会顺带修复 |
| 4 | 旧版 anon key 暴露了 Supabase 项目地址，可绕过中转直连数据库 | 所有规则放在数据库内部（绕过中转也拿不到额外权限）；换用新版 publishable key |
| 13 | Gemini 公开分享链接泄露了服务器信息 | 删除链接，并轮换订阅地址和面板入口（第 0 步、第 9 步） |

顺带修复了一处：被隐藏的帖子，其下的回复现在也不可见、不能再被回复。

**需要提前知道的变化**：使用暗号的人，在新版里第一次发言时会拿到一个**新号码**，之后就固定不变。旧算法本身不安全，没办法安全地把旧号码迁移过来。

## 第 0 步：删除 Gemini 公开分享链接（最先做）

打开 Gemini → 设置 → 找到“公开链接”（Public links）管理页 → 删除那条“Python树洞论坛技术栈规划”的链接。

链接存在期间，内容可能已经被别人看过，所以第 9 步的轮换仍然要做。

```powershell

```

```powershell

```

看到 `✓ Compiled successfully`（或类似的成功提示）就可以继续。如果报错，把完整输出发给我。

## 第 2 步：在 Supabase 运行第 1 段 SQL

1. 打开 Supabase 控制台 → 左侧 **SQL Editor** → **New query**
2. 用编辑器打开 `H:\pisces\supabase\migrations\20261010000100_p0_rpc_identity.sql`，全选并复制
3. 粘贴到 SQL Editor，点击 **Run**
4. 看到 `Success` 即可（结果区可能显示一行“重新分配了 N 个可疑号码”，这是正常的）

这一步只做增量修改，**旧版线上网站在执行后仍然可以正常使用**。

## 第 3 步：本地测试新版前端

```powershell
npm run dev
```

打开 http://localhost:3000，逐项确认：

- [ ] 页面能正常显示帖子和回复
- [ ] 不填暗号发一条：显示为一个新号码
- [ ] 填一个暗号，连续发两条：两条是**同一个号码**（第一次带暗号发送会多等 0.3–1 秒，这是 PBKDF2 计算的正常耗时）
- [ ] 用同一个暗号回复别人的帖子：号码不变
- [ ] 按 F12 → Network，点开 `create_post` 请求：请求体里只有 `p_content` 和一串 64 位的 `p_key`，**看不到暗号原文**

## 第 4 步：换成新版 publishable key

1. Supabase 控制台 → **Project Settings → API Keys**
2. 切换到新版密钥（Publishable and secret API keys）页签；如果还没有，点击创建
3. 复制 **publishable key**（以 `sb_publishable_` 开头）。⚠️ 不要复制 secret key，那是服务端用的，绝不能放进前端
4. 打开 `H:\pisces\.env.local`，新增一行：

   ```
   NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY="sb_publishable_你的key"
   ```

   旧的 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 这一行先保留，代码会优先使用新 key。
5. 在终端按 `Ctrl + C` 停止开发服务器，再重新运行 `npm run dev`，重复第 3 步的测试
6. 如果出现 `Invalid API key` 或 401：先删掉刚加的那一行恢复原状，然后把报错发给我（问题可能出在 Nginx 中转上）
7. 测试通过后，到 Vercel → 你的项目 → **Settings → Environment Variables**，新增同名变量 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`（Production 和 Preview 都勾选）

## 第 7 步：关闭 Supabase 用户注册

这个网站不使用登录功能，但 Supabase 默认允许任何人通过 API 注册账号。别人可以借此批量注册，并让你的项目替他们发送验证邮件。

Supabase 控制台 → **Authentication → Sign In / Providers** → 关闭 **Allow new users to sign up** → 保存。

## 第 8 步：停用旧版 anon key

确认线上网站已经在使用新 key（第 5 步部署成功，并且第 6 步之后仍然正常）：

1. Supabase → **Project Settings → API Keys** → 旧版密钥（Legacy API keys）页签 → 停用（disable）JWT 类的旧密钥
2. 删除 `.env.local` 里的 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 那一行，Vercel 环境变量里如果有同名变量也删掉

停用之后，旧版网页代码里那把带项目编号的 key 就失效了。停用是可逆的：万一网站出问题，在同一位置重新启用即可。

## 第 9 步：轮换 VPS 上被泄露的入口

分享链接里出现过：VPS 的 IP、x-ui 面板的端口和路径、订阅链接（含路径令牌）。IP 没法轻易更换，但其余几项都应该换掉。

**顺序很重要：先在防火墙上开新端口，再改面板端口，否则可能把自己锁在外面。**

1. **DigitalOcean 防火墙**：Networking → Firewalls → Inbound Rules → 新增一条 TCP 规则，端口填一个新的随机端口（例如 20000–60000 之间的任意数字），先**不要**删除旧规则
2. **x-ui 面板 → 面板设置**：
   - 把面板端口改成刚才开放的新端口
   - 把面板路径（URL 根路径）改成一串新的随机字符
   - 修改面板的登录用户名和密码
   - 保存并重启面板，然后用新地址登录确认
3. **订阅设置**：把订阅路径改成新的随机字符串，保存
4. **入站列表**：编辑每个节点里的客户端，重新生成 UUID（以及订阅 ID），保存后**重启 Xray**
5. 在 v2rayN 里把订阅地址更新为新路径 → 更新订阅 → 确认节点能连通
6. 一切正常后，回到 DigitalOcean 防火墙，删除旧面板端口（7777）的入站规则

万一改完后面板打不开：SSH 登录服务器，输入下面这条命令，进入 x-ui 的命令行菜单查看或重置面板设置：

```bash
x-ui
```

Supabase 的项目编号无法更换，所以按“已经公开”处理。它的风险已经由第 2、6、8 步兜住了。

## 自查（可选）

在 SQL Editor 里运行下面两句。访客（anon）应该只剩 posts / replies 的几列读取权限，以及两个发帖函数的执行权限：

```sql
SELECT grantee, table_name, column_name, privilege_type
FROM information_schema.column_privileges
WHERE table_schema = 'public' AND grantee IN ('anon', 'authenticated')
ORDER BY grantee, table_name, column_name;
```

```sql
SELECT routine_schema, routine_name, grantee
FROM information_schema.routine_privileges
WHERE routine_schema IN ('public', 'private') AND grantee IN ('anon', 'authenticated', 'PUBLIC');
```
